# 总控分工与交互 · V0.7

本版把已装配员工和 Skill 形成可审阅的执行分工。入口是 **新建目标 → 选择员工 → 创建 → 任务 → 总控分工**，保留原有新建目标、群聊及直接确认计划流程。

## 一、两种分工方式

**基础分工**不需要模型额度：按已选员工的能力列任务，专业员工在前、协调汇总在后。它不理解所有复杂目标；用户应确认所选能力是否覆盖需求。不会默认为复杂业务做出准确规划。

**模型分工**使用“能力中心 → 模型连接”里当前版本测试通过的连接，支持已有 API / 本机 Codex 接入。总控发送用户目标、店铺 / SKU 范围、成员及其已装配能力的名称、描述和所需字段，不发送账单、知识库正文或会话全文。只做一次有时限的结构化规划调用，不调用工具。API 输出上限 4000 token；不是无界自主循环。

模型只能为已选成员各安排一步，调整先后、选择每人已有能力的子集，填写具体任务与交付标准。不允许加入新员工、重复安排员工、凭空发明能力，也不能覆盖业务数据。JSON 无效或越权时整份结果拒绝，不自动降级冒充模型成功。此边界便于先实现可控协作；动态分支、一个员工反复参与多个步骤和自主扩编尚未实现。

模型真实服务尚未用用户账号联调。自动化以受控模型响应验证协议、约束和执行；静态 HTML / GitHub Pages 只能生成基础分工。

## 二、点击后会发生什么

| 操作 / 条件 | 系统动作与结果 | 用户下一步 |
|---|---|---|
| 点击“生成分工并检查资料” | 按所选模式生成草案，检查本地能力输入，保存目标版本及成员配置版本；不改原执行顺序、不启动员工 | 审阅步骤、交付标准和检查结果 |
| 当前目标正在生成 | 禁用当前页面重复操作；后端拒绝同目标并发生成 | 等待；可切换页面，结果保存回原目标 |
| 本地账单等必填字段缺失 | 对应能力列为“待补资料”，显示缺项；不以 0 代替未知值 | 去“资料”上传 / 填写真实数据并保存 |
| 售后能力或外部能力 | 售后检查问题和已选知识库是否有启用文档；外部只检查配置就绪。本轮不请求外部 Agent，也不构建向量索引 | 运行时再检查实际召回与外部业务输入 |
| 点击“采用这份分工” | 后端再次校验草案 ID、目标版本、员工配置和能力范围；保存执行计划并调整交接顺序，目标版本加一 | 再点击“确认计划”才启动执行 |
| 点击“放弃草案” | 删除当前待审草案，保留原已采用分工 / 原成员顺序，不改变业务资料 | 可直接确认原计划或重新生成 |
| 尚有待审草案时确认计划 | 页面禁用确认；后端也拒绝绕过 | 先采用或放弃草案 |
| 没有草案也没有采用分工 | 保留 V0.6 行为，按所选成员与装配列表执行 | 可直接确认，不强制使用规划功能 |
| 点击“确认计划” | 按采用的步骤顺序依次执行，每步只开放该步骤选中的能力；前序交付进入后序观察输入 | 在任务 / 交付物 / 运行记录查看结果 |
| 执行返回待补资料 / 失败 | 停在当前步骤，保留已有记录和缺项，不伪造成功、不自动发起外部写入 | 补资料重新确认，或排查配置后重试；需更改分工时点击“重新安排分工” |

检查列表是生成草案时的快照，标记“输入校验通过”不等于事实真实、数据完整或业务结论正确。检查调用本地只读校验 / 计算并只保留检查状态，不把检查结果作为正式交付；正式执行仍重新计算。采用分工允许保留待补项，但正式步骤遇到缺项仍会停住。

## 三、变更和异常

- 保存商品、账单、业务输入、知识范围、素材引用或方案变更，会使当前分工草案与已采用计划失效，回到待确认阶段。请基于新资料重新生成；原有运行轨迹仍保留。
- 失败或待补资料时可点击“重新安排分工”：保留业务资料，旧草案标为历史，回到待确认阶段。正在运行 / 排队的任务不能用此操作绕过执行状态。
- 修改员工、员工模型或挂载外部能力的配置版本后，旧分工不能被采用 / 启动。排队后变更也会在运行前被检查，运行期间的配置变化在后续调用和结果接收时检查。
- 计划生成过程中改动资料、暂停目标、开始执行或修改成员配置时，旧响应不会替换当前计划。
- 目标暂停时不能生成或采用分工；已交付、已验收目标不能重新安排执行，需创建下一轮目标。
- 模型超时、未配置、无效 JSON、工具调用或越权能力均显示错误，原有草案 / 计划保持不变。没有凭据时只能选择基础分工；后端不接受伪造的模型 ID。
- 服务重启保留已保存草案与采用计划。尚在请求中的规划没有完整结果则不写入，需重新生成；不会自动执行残缺分工。
- 资料检查只反映当时状态；知识文档是否匹配、外部响应、引用版本和业务结论仍在实际执行时核验。

## 四、群聊与外部协作

在目标群里发送给“数字员工协调”，询问“现在进度如何”“还缺什么”“下一步是什么”，系统会读取当前阶段、已完成员工、下一位处理人、最新缺项和阻塞原因，直接回答，不重跑计算。定向 @ 员工仍按原来的员工提问流程处理。该进度查询采用明确的词项匹配，不冒充模型理解。

本步分工以 `input.assignment` 进入员工执行快照，包含 employeeId、employeeName、objective、deliverable、skillIds。模型员工可据此处理具体任务，但可调用工具严格限定为已确认子集；代码员工仍按固定代码逻辑处理业务资料，不把自然语言步骤当作任意代码执行。

外部 Dify / HTTP 如需接收本步说明，可以在接入配置中勾选 **已确认的本步分工**（`assignment`）。原连接不会自动获得这个新字段；保存后需重新测试。外部服务仍使用原有输入字段白名单和只读约束。

## 五、接口与持久化

生成：`POST /api/goals/:id/planning`

```json
{"expectedVersion": 2, "mode": "rules"}
```

模型方式用 `mode: "model"`，并传 `modelId`。返回更新后的目标，含 `planProposal`，尚未执行。

采用 / 放弃：`POST /api/goals/:id/actions`

```json
{"kind":"adoptPlan","expectedVersion":2,"proposalId":"本次草案ID"}
```

放弃使用 `kind: "discardPlan"`。采用后的 `executionPlan` 保留来源模式、模型标识与版本（不含密钥）、生成时间、步骤、确认事项、检查快照和采用时间。确认计划仍使用原 `kind: "plan"`。

没有把第三方服务部署成新 Agent，也未新增店铺写入。V0.7 在 V0.6 的 14 个代码 Skill、Dify / HTTP 适配器和知识库上增加总控规划和检查，不能据此声称全部 134 项规划能力已完成。

## 六、验收证据

74 项自动化测试通过：含本版 9 项测试，覆盖分工边界、实际能力子集执行、资料与配置失效、并发生成、无效模型输出、重启恢复和无额外调用的群聊状态查询。模型测试使用受控响应，未声称完成用户模型连接。

服务器版与断网预览浏览器流程：创建盈亏分析 + 协调团队 → 缺资料检查 → 放弃草案 → 上传 CSV → 检查通过 → 采用分工 → 确认执行 → 得到 3300 元虚构账单贡献利润 → 群聊查进度。检查 375 / 768 / 1440 宽度、键盘焦点、减少动画模式与页面运行错误。
