# 原型架构（2026-11-05）

## 一个目标，多种业务视图

新版 `src/goals.js` 定义 Goal 聚合：业务范围、完成标准、负责岗位、可选Agent、任务依赖、商品事实、群聊、版本化成果、审批、执行回执、观察复盘和审计。群聊不是任务状态本身；所有页面按同一聚合投影。

HTTP服务和离线HTML复用同一领域代码。服务端通过串行命令链克隆状态、校验转换、写快照、原子rename、更新内存后响应，避免一次命令失败后写入半份目标。离线版采用同样的克隆后更新逻辑，使用localStorage。两者不跨端同步。

## 原型与生产的区别

原型主流程由显式按钮驱动，回复由有界队列和确定性模板模拟。它不是已接入大模型的自主经营Agent。原型只能验证用户是否理解目标、等待、审批、核验和复盘的关系。

未来每个目标的主协调者从持久化任务状态唤醒，读取已确认资料，调用专业Agent/Skill/工具，消费结构化结果，更新状态或等待外部事件。多个目标可以独立运行，同一SKU的写操作通过锁/版本控制冲突。等待审批和资料时保存检查点，不持续空转推理。

## 状态与执行防护

- 发布路线：资料→计划→草案→审批→待提交→待核验→观察→验收→结束。
- 草案路线和分析路线不创建发布审批。
- 审批保存动作快照、approvalId和版本；修改标题或售价生成新版本，旧审批失效。
- 重复提交在待核验阶段复用executionId。回读失败只允许重试核验，不重复发布。
- 暂停目标阻止业务推进；暂停回复仅保留聊天队列。已提交动作不能被“暂停”撤回。
- 聊天背景不直接覆盖商品事实；变更请求需结构化确认。
- 全部发布、验证及账单为虚构样例，不连接外部系统。

生产需额外实现：身份与租户隔离、权限与成本/预算规则、动作指纹和通用请求幂等、数据库事务与并发版本、平台异步回执、外部超时未知态、任务重放和补偿、真正不可篡改审计、模型/工具预算、真实数据口径与证据保全。

## 持久化与历史

新版服务数据 `.data/goals.json`；旧版 `.data/tasks.json` / `.data/rooms.json` 保留且兼容API仍可读。旧房间缺少验收标准及范围，不自动伪造目标关联。新版UI只读取新Goal。

浏览器独立原型键 `muyaju-goals-v1`。旧版存储键保留，不清空历史。更换HTML所在路径可能改变file来源存储范围，真实部署应采用明确origin和数据库存储。

## 验证

领域测试覆盖资料前置、版本和动作绑定、退回、只准备草案、重复提交、回读异常、观察验收、消息边界和独立暂停；既有引擎测试保留。浏览器验证离线/服务端完整流程、草稿切换、输入转义、成果下载、刷新恢复、375/768/1440宽度和手机目标详情。浏览器禁止file协议访问，因此离线自动化以路由直接返回单文件HTML并拦截其他网络请求，验证其无需后台或外部资源。
