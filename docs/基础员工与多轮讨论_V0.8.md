# 基础员工与多轮讨论 · V0.8

更新：2026-11-07。目标是先让岗位可选、能力可执行、群聊能持续协作，再逐步增强模型能力。

## 1. 基础员工开箱可用

新工作空间默认创建 12 类员工，每位至少装配一项实际代码能力；默认不依赖模型密钥。旧空间只补齐缺失岗位，不覆盖同岗位已有员工、停用状态或自定义配置。若原员工配置未就绪，仍需检查其设置。

| 岗位 | 当前能做的基础工作 |
|---|---|
| 市场研究 | 比较用户提供的候选商品参数和价格，不自动联网调研 |
| 选品规划 | 按提供的评分计算加权排名，并比较参数 |
| 商品管理 | 校验商品事实，编排有来源的上新草案 |
| 内容创意 | 详情页文字大纲、有限宣传声明初筛 |
| 流量推广 | 核算 CTR、转化率、CPC、CPA、ROAS，提示漏斗排查项 |
| 活动运营 | 对比折扣利润、保本销量与预算风险 |
| 供应链协同 | 按库存、日销和交期计算覆盖与缺货风险 |
| 客服售后 | 客户问题关键词分诊、所需凭证清单、接待话术 |
| 价格与利润 | 录入账单贡献利润 / 上新采购价差计算 |
| 经营分析 | 按录入经营账单核算贡献利润并说明口径 |
| 运营协同 | 整理目标、范围和前序交付，汇总待确认项 |
| 运营风控 | 初筛有限宣传词并列出人工核验项，不保证全面合规 |

当前共 **16 个可执行代码 Skill**。已有 SKU 盈亏、批量补货、知识库售后答复等工作包可继续单独装配。12 类基础员工不等于方案中的 134 项专业能力已经实现；基础员工按固定逻辑处理，不能替代已接模型的自由对话、语义判断和完整业务执行。

进入“数字员工”后可以：

1. 点 **试运行**：使用明确标注的虚构样例验证能力，查看真实计算 / 整理结果。
2. 点 **交给他一个目标**：打开保留的新建目标入口，预选该员工；创建后补资料、确认计划、查看交付。
3. 进入已有目标的讨论区，点 **邀请员工**，加入群聊后直接 @ 提问。

推广数据需同一归因口径，曝光 / 点击 / 订单为非负整数且订单 ≤ 点击 ≤ 曝光。分母为 0 时不制造比率；ROAS 不是利润。客服分诊只生成待核实信息与接待草案，不承诺退款 / 换货资格，不发送客户消息。普通承接性追问可参考选中上下文里的上一条人类问题，结果会注明参考内容；仍是规则判断。

## 2. @ 与群聊交互

- 输入空格后的 `@` 或以 `@` 开头，弹出本群员工候选；可继续输入姓名筛选。
- 上下方向键切换，Enter 选择员工，Escape 关闭。候选打开时 Enter 不会直接发送消息；中文输入法组词期间不抢占 Enter。
- 点击候选会插入完整名字并将“发送给”切回协调入口；一次最多 @ 4 人，各自回复同一条消息。多人回复按队列逐个处理，不是并行调用。
- 非群成员先点“邀请员工”。新成员加入讨论后可选可 @，**不加入目标执行成员、不改变已确认分工**。讨论最多 24 位员工，单目标执行成员仍最多 8 位。
- 同名员工必须从候选列表选择，后端用成员 ID 消歧。未知名字、未邀请成员、@ 与接收者冲突、消息超过 2000 字或队列已满，会明确报错，不静默发给错误的人。
- 点击消息下方“引用回复”，再输入问题，会保存引用关系并优先路由给被引用回复的员工。普通“那…… / 刚才…… / 继续……”追问可沿用上一位处理人；上一轮有多人时提示选择 @ 或引用。
- “你能做什么 / 你是谁 / 需要哪些资料”等询问直接介绍该员工已装配能力；“进度如何 / 还缺什么”等协调提问读取当前状态，不重跑业务计算。
- @ 名称不会作为客户业务问题传给分诊 / 检索，防止姓名或岗位名干扰分类。原始消息仍完整保存。

邀请的员工所需结构化输入也会显示在目标资料区。基础商品事实仍受目标类型和确认流程约束；若新工作需要另一种完整业务流程，可从该员工入口新建目标。

## 3. 会话存在哪里

| 使用方式 | 保存位置 | 范围 |
|---|---|---|
| 完整服务器版 | `.data/platform.json`，或 DATA_DIR 对应目录 | 目标、人类消息、员工回复、引用、成员、上下文设置及运行快照；刷新和重启后恢复 |
| GitHub Pages / HTML 预览 | 当前浏览器、当前来源的本地存储 | 可刷新恢复；不同网址、浏览器和电脑不互通，清除站点数据会丢失 |
| 浏览器不允许本地存储 | 页面内存，预览顶部提示 | 刷新后丢失 |

点击 **导出对话** 下载此目标的 JSON，包含原消息、引用关系、时间和上下文设置。当前没有导入、跨设备同步或聊天数据库；不能把导出文件当作平台完整备份。服务器运行数据不会提交 GitHub，克隆代码不包含测试会话。这也不会把用户与 Codex 的开发聊天导入平台。

## 4. 上下文如何筛选

完整历史和模型输入分开：消息全部保留，每次回复从同一目标筛选有限上下文，并将选择结果保存到运行输入。

筛选次序：

1. 保留本次问题，不带入它之后才出现的消息。
2. 优先引用链（最多回溯 4 条）及用户固定的消息。
3. 最近 4 条符合条件的对话。
4. 与本次问题词项相关的历史，再按近期顺序补充。
5. 按消息数与字符预算裁剪，最后按时间顺序组织；单条历史最多 2000 字符。

默认每轮最多 12 条 / 12000 字符，可改为 6 / 12 / 20 条，字符预算 4000–24000。这里是字符预算，不是精确模型 token 数；固定背景另计最多 2000 字符，结构化业务资料和交付物不包含在这项历史预算中。

过滤条件：不使用另一目标的聊天；不使用已排除消息及其后续引用回复链；不使用新话题边界前的消息；旧业务版本 AI 回复、失败或已丢弃回复不作为有效历史。旧人类消息仍可作为带来源的讨论背景，不能覆盖当前确认的业务字段。

这是本地规则与词项筛选，不是模型语义摘要、长期智能记忆或完整话题聚类。已接模型的员工实际收到筛选后的历史与固定背景；代码员工只在其能力允许范围内处理这些输入。

## 5. 上下文按钮和异常处理

| 操作 | 行为 |
|---|---|
| 消息 → 固定上下文 | 优先带入后续对话，最多 6 条；旧话题、旧版本 / 失败回复不能固定 |
| 消息 → 不带入上下文 | 消息保留，但后续筛选排除它及其引用后代；可点恢复 |
| 顶部 → 上下文 | 查看预计选中的消息及原因，修改固定背景、条数和字符预算 |
| 保存上下文设置 | 版本加一；不修改商品、账单等已确认业务事实 |
| 开始新话题 | 清除固定背景和固定 / 排除项，设置新的对话起点；历史与业务资料仍保留 |
| 生成回复期间修改上下文 | 尚未调用的旧请求不再发出；已发出不能撤销，但旧返回不会被采纳为有效回复 |
| 引用被排除消息 / 旧话题 | 明确拒绝，提示重新说明必要背景 |
| 同时编辑设置 | 版本冲突提示重新打开，不覆盖另一份设置 |

固定消息也可能因为引用优先、总条数或字符预算被截断 / 未带入。上下文窗口显示预览，真正发送内容以 **运行记录 → 输入 → conversation / contextSelection** 为准。外部 Dify / HTTP 如要接收多轮历史，需明确勾选“本轮筛选后的对话”和“固定背景与筛选规则”，保存并重新测试；旧连接不会自动得到新字段。

## 6. 接口与验证

- `POST /api/goals/:id/actions`，`kind: inviteDiscussion`，传 `employeeId`。
- 同一路径 `kind: message`：支持 `text`、`target`、`intent`、`mentionIds`、`replyTo`。
- 同一路径 `kind: chatContext`：带当前 `revision`，可更新 `note`、`maxMessages`、`maxChars`、`pinnedIds`、`excludedIds`；`reset: true` 开始新话题。
- `GET /api/goals/:id/context?question=...`：预览筛选；不保存，不调用模型。

新增 8 项自动化测试覆盖基础员工样例、升级保留配置、推广计算、@ 消歧、多人回复、持久化、上下文预算 / 截断 / 过滤、追问路由以及运行中切换话题。82 项回归测试通过；模型上下文测试使用受控响应，未接用户真实账号。

浏览器验证服务器版和断网预览：@ 键盘候选、邀请、多人回复、引用、固定、上下文设置、刷新恢复、导出、新话题及 375 / 768 / 1440 宽度。测试环境 Chrome 禁止 file:// 导航，断网预览通过在本地测试来源提供相同 HTML 验证，没有调用真实后端或外部模型。
