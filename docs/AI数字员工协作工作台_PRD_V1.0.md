## 1. 产品定位与核心决策

面向电商运营负责人，用自然语言交代目标，由数字员工组织任务、协调专业 Agent、等待资料和审批、核验动作结果，并记录经营复盘。业务负责人始终能看到：在做什么、为什么、卡在哪里、需要自己做什么、实际得到什么结果。

**“新建目标”是创建业务对象的动作；“协同工作台”是围绕该对象持续工作的空间。两者保留，并明确分工。**

群聊承担沟通入口。任务、审批、商品事实和验证记录承担业务状态。普通消息不会隐式修改商品资料，不会把“好的”当作发布授权，也不会因所有 Agent 回复结束而宣告目标完成。

采用一个目标的主协调者 + Loop，按需调用不同 Agent/Skill/工具。UI 可以有多个参与者；后台不需要十二个独立 Agent 不断互相聊天。各目标隔离上下文，针对同一 SKU 的写入另做冲突控制。

## 2. 用户、场景与成功标准

| 用户 | 主要诉求 | 产品支持 |
| --- | --- | --- |
| 经营负责人 | 给出目标、控制成本风险、验收价值 | 新建目标、明确边界、审批动作、复盘 |
| 商品/内容运营 | 核实规格、准备内容、定位阻塞 | 商品资料、任务依赖、版本化交付物 |
| 客服/供应链协作者 | 回答具体问题、提供事实 | @、缺资料卡、协同待办（真实多人后续实现） |
| 平台管理员 | 管理模型、系统权限、运行质量 | 连接状态、能力配置与审计（逐期接入） |

产品验收不使用“机器人发言数”或“建议文本数量”。生产指标应包括有证据的任务完成率、人工等待时间、发布核验成功率、审批后错误率、SKU贡献利润、节约时间及其统计口径。原型只验收交互和状态一致性。

## 3. 本期范围与后续边界

### 3.1 本期实现

1. 保留全局“新建目标”，两步创建：描述目标和团队 → 确认业务范围和执行边界。
2. 两种模板：商品上新、经营分析。用户自行确认模板；模板选择不是大模型语义理解。
3. 一个目标同时关联协作空间、任务、资料、交付物、审批、执行回执与复盘；各页面读取同一份状态。
4. 群聊支持人类发言、默认交给数字员工协调、@已选成员、补充背景/讨论/变更请求、暂停回复。
5. 商品上新样例：缺资料 → 确认演示资料 → 确认计划 → 草案 → 审批 → 提交 → 回读 → 观察 → 复盘验收。
6. 审批绑定动作版本；修改发布内容使旧审批失效。支持退回、暂停目标、回读异常和重试回读。
7. 经营分析和“只准备草案”不进入发布路径。
8. 全局任务、交付物和目标内标签一致；交付物可预览下载；刷新保存。
9. 单文件 HTML 可独立打开，服务端版使用同一领域逻辑。

### 3.2 本期不承诺的业务能力

真实模型推理、真实电商 API、自动经营巡检、多用户在线、组织权限、真实投放/调价、生产级工作流与数据库事务均未接入。演示回复是模板，商品资料和经营账单为虚构数据，发布和回读是模拟动作。页面需持续显示“演示模式”，操作按钮明确使用“模拟”或“演示”。

持续经营目标、机会自动发现、期限催办、真实规格资料上传、多人委派、本期以设计说明和机会样例呈现；不提供看似已启用的假开关。通用自然语言目标进入分析模板时，提示其任务计划只是示例，真实动态拆解后续接入。

## 4. 信息架构

本期保持五个一级入口，避免将每个后台模块展开为独立菜单：

- **协同工作台**：左侧目标列表；中间目标协作区；右侧目标摘要。
- **任务中心**：跨目标的任务列表；可筛选待我处理（资料、计划确认、审批、最终验收）、执行中、已完成；点击回到相应目标任务。
- **数字员工**：业务负责岗位与专业 Agent 的关系、参与能力和可用状态。
- **交付物**：跨目标成果；显示目标、版本、草案/已验收/已核验/已替代。
- **连接与设置**：数据与模型连接状态；明确待接入项。

“新建目标”固定在侧栏，并在手机页头保留。商品资料归属于目标内的“资料”标签；有多个真实商品后再独立升级成“商品与知识”。经营总览待真实指标接入后建设，不以虚构业绩数字装饰首页。

目标内部标签：**讨论｜任务｜交付物｜复盘｜资料**。切换标签不建立新任务；所有标签都保留目标身份。手机端右侧摘要折叠为可访问的“目标详情”，不能直接隐藏掉关键范围与约束。

## 5. 新建目标：两步渐进确认

### 5.1 第一步：描述目标和协作团队

- 标题“交给数字员工一个目标”；自然语言输入必填，1–2000字。
- 模板选择“经营分析 / 商品上新”，旁有清晰说明。示例机会卡可直接预填商品上新。
- 显示负责岗位建议：商品上新→商品运营数字员工；分析→经营分析数字员工。
- 可增删经营分析、商品运营、内容营销、客户服务 Agent，至少一位；未参与的 Agent 不出现在 @ 列表。
- 按钮“下一步：确认范围”。第一步不创建目标、不触发执行。

### 5.2 第二步：确认范围和执行边界

展示刚才的自然语言目标、平台/店铺、SKU或店铺汇总、预期交付与观察窗口。原型范围只提供明确标记的虚构样例，不能误认为已读取用户真实店铺。

商品上新提供两种边界：

1. 只准备草案：资料→计划→草案→人工验收，绝不出现发布审批或模拟已上架。
2. 发布前逐次审批：资料→计划→草案→精准审批→模拟提交→回读→观察→验收。

经营分析固定只准备建议。未来 L1–L5 权限在策略层强制执行，UI选择不是权限证明。

第二步显示“商品资料待核验”，允许先建立目标，随后停在等待资料状态。点击“创建目标并进入协作”一次性建立目标、关联群和任务，返回目标的讨论页。提交时防重复点击，失败保留输入并显示原因。返回第一步不丢输入；取消不创建数据。

### 5.3 一次性与持续经营的区别（P1）

本版创建一次性目标。持续经营未来增加巡检频率、触发阈值、预算、截止时间、停用条件；每次巡检产生有证据的候选任务，不重复建立无关聊天群。等待期间保存检查点，由数据/定时/人工事件恢复，不持续空转推理。

## 6. 群聊交互

| 人类操作 | 系统行为 | 不能隐式发生的行为 |
| --- | --- | --- |
| 普通讨论 | 默认主协调者回复；可按需调用专业能力 | 不给所有 Agent 广播，不自动生成新交付物 |
| 选择接收者或 @成员 | 由该成员处理，消息关联原发言 | 不改变成员权限，不添加未邀请的 Agent |
| 选择“补充背景” | 消息保存为上下文，回复确认收到 | 不直接覆盖权威规格、成本、库存 |
| 选择“请求变更” | 记录请求，提示用结构化入口确认 | 不凭聊天文本自动变更审批动作 |
| 点击“调整发布内容” | 编辑标题/售价，确认后新版本、重新计划与审批 | 旧审批不得继续执行 |
| 暂停AI回复 | 队列保留，人类可继续发消息 | 不代表停止已经提交的平台动作 |
| 暂停目标 | 阻止新的计划推进和模拟执行，讨论仍可继续 | 不能撤回外部已提交请求 |

消息需要角色、时间、原回复关联、演示标记。中文输入法组合状态不触发 Enter 发送，Shift+Enter换行。发送后清除已提交的文本，但发送过程中输入的新内容保留；失败保留原消息并提示重试。每目标维护草稿、接收者和阅读位置，轮询不得抢焦点或把读历史的人拉到底部。

本版“人类”只有当前浏览器用户身份。未来多用户需要会话鉴权、成员身份、权限、消息排序和SSE/WebSocket；不能仅修改头像就声称多人协同已完成。

## 7. 商品上新贯通交互

### 7.1 资料等待

首个任务为“核验商品事实”，显示SKU、材质、接口、成本、库存、来源、更新时间。未核验时所有关键字段为待确认，禁止生成可发布规格。原型通过“载入并确认演示资料”填充虚构样例：黄铜、G1/2、成本12元、库存200件，并记录确认人、时间、来源 DEMO-SPEC-001。

未来使用资料上传/ERP关联/向责任人请求补齐；互相冲突的来源必须人工消歧。规格不得依赖语言模型猜测。

### 7.2 计划确认

任务按依赖显示，卡片含负责 Agent、状态、前置步骤和完成标准。点击确认计划进入草案准备。当前v版本始终可见。未选择某专长时由已选团队承接，不悄悄邀请未选 Agent。

### 7.3 交付物准备

点击“生成演示草案”生成带taskId、goalId、版本和来源的内容。先预览后审批。上新草案含标题、SKU、规格和售价；分析目标含建议结构与数据限制。

每次聊天回复不自动成为交付物。交付物是任务的显式产出。全局交付物与群内产物使用同一个artifactId。

### 7.4 发布审批

审批卡必须显示：

- 动作：新增商品发布；执行模式：模拟。
- 店铺、SKU、当前版本。
- 变更前：无平台商品；变更后：拟发布标题和售价；规格来源。
- 库存和成本、审批影响：仅该商品本次发布，不包含广告预算、调价和后续自动操作。
- 风险说明：成本不是完整贡献利润；未含运费/平台/广告/退款前不能据此判断净贡献。
- 操作：批准此版本 / 退回修改 / 调整发布内容。

批准只是将状态改为待提交，另点“模拟提交发布”后才创建执行回执。批准请求携带approvalId和version，服务端再次核对。修改标题/售价升级版本并失效旧审批，保留旧版本交付物为已替代。退回必填原因，再次准备后重新审批。

### 7.5 提交与核验

“模拟提交”生成唯一执行ID、幂等键、演示回执。重复点击不重复生成执行记录。UI状态为“已提交，待核验”，不能写成已上架。

回读比对店铺、SKU、标题、售价、可售状态。原型提供“模拟核验通过”和“演示回读不一致”两个测试入口。不一致时保持待核验并展示错误，之后“重试回读”复用同一执行，不再次发布。真实接口后续还需处理超时未知态、平台异步审核、部分成功和人工接管。

### 7.6 观察和复盘

核验成功只代表业务动作通过，接着进入观察中。原型用“载入7天演示观察数据”明确跳过真实时间等待，不显示假倒计时。没有数据时显示等待，不能当作零收入。

复盘样例：净销售额3000；商品成本1200；平台/支付费用150；履约300；归因广告600；售后额外损失150；其他可变费用0；贡献利润600，贡献利润率20%。净销售额已扣退款本金，售后损失只记额外成本，避免重复扣减。

所有数字标注虚构。目标阈值15%是演示假设，可说明样例达标；无真实基线和对照，不能写“利润提升20%”或归因于AI。生产需记录数据更新时间、订单范围、费用归因和观察窗口完整性。

负责人点击“确认复盘并结束目标”后才结束。结束后讨论保留，任务完成，交付物保持最终状态。可以“创建下一轮优化目标”，创建新的分析目标并记录来源目标，不篡改已结束目标。

## 8. 状态机与异常规则

发布路径：

```text
等待资料 → 待确认计划 → 待准备草案 → 待审批 → 待提交
→ 已提交待核验 → 观察中 → 待复盘验收 → 已结束
```

草案路径：等待资料 → 待确认计划 → 待准备草案 → 待验收 → 已结束。
分析路径：待确认计划 → 待准备建议 → 待验收 → 已结束。

| 事件 | 处理 |
| --- | --- |
| 核心资料未确认 | 停留等待资料，不能跳步 |
| 审批退回 | 记录原因，重新计划，递增版本，旧草案保留为已替代 |
| 审批后修改内容 | 审批失效，不能提交，重新确认新版本 |
| 重复模拟提交 | 返回已有执行状态，不重复执行 |
| 回读不一致 | 等待核验，提示差异，支持仅重试回读 |
| 目标暂停 | 阻止业务推进，讨论和资料查看继续 |
| 回复暂停 | 不消费回复队列；不改变目标状态 |
| 连接失败 | 保留表单、草稿，显示错误，刷新恢复；不能用旧状态伪装成功 |
| 页面刷新/服务重启 | 恢复持久化目标状态，不自动越过审批 |
| 目标结束 | 保留讨论和成果；新工作另建目标 |

原型是确定性状态机。未来运行时还需独立Run的失败、超时、补偿、取消状态，不能把它们都映射成一句“失败了”。

## 9. 对象与数据契约

| 对象 | 核心字段 |
| --- | --- |
| Goal | id、自然语言、类型、scope、criterion、owner、成员、permission、version、stage、paused |
| Collaboration | roomId、goalId、messages、回复队列、repliesPaused |
| Task | id、goalId、title、owner、dependsOn、status |
| ProductFacts | SKU、材质/接口、成本/库存、来源、确认人/时间 |
| Artifact | id、goalId、taskId、version、status、body、evidence |
| Approval | id、version、payload快照、status、审批人/时间/退回原因 |
| Execution | id、幂等键、version、submittedAt、receipt、verifiedAt、evidence/error |
| Review | 观察窗口、各收入费用、利润和口径、基线、阈值、结果与来源 |
| Audit | 操作人（当前为你）、action、version、时间、摘要 |

原型为每Goal内聚存储关联对象，整体JSON原子替换，前端按同一对象投影。服务端与单文件共享src/goals.js的状态转换；旧版rooms/tasks数据保留文件但不自动推断为新目标，避免伪造历史业务关联。离线版与服务端数据独立，不做跨端同步。

接口：GET/POST /api/goals；POST /api/goals/:id/actions。动作包括message、pauseReplies、pause、facts、plan、draft、revise、approve、reject、execute、verify、observe、complete。实际生产应拆分命令和查询，加入用户身份、租户、请求幂等、乐观锁、权限和数据库事务。

## 10. 单 Agent + Loop 的生产演进

```text
人工目标 / 数据事件 / 定时巡检
  → 目标与任务状态库
  → 该目标主协调者读取事实和检查点
  → 判断下一步 / 调用专长 Agent 或工具
  → 权限和业务规则网关
  → 结构化结果 + 证据 + 版本
  → 状态更新 / 等待 / 复盘
  → 群聊事件卡与任务视图同步
```

主协调者负责按状态推进，不把模型输出直接当执行指令。需要资料、审批、外部结果时持久化等待，相关事件到来才继续。循环限制包含步数、时长、工具调用/模型费用；真实外部写入须校验授权范围、库存成本规则、动作版本、幂等键并回读。用户在群内可见业务活动，不必暴露内部推理链。

## 11. 视觉与无障碍规范

- 黑白灰为结构，蓝色 #315DDD 为唯一主色。纯文字产品名，无字母logo、星环和装饰性拟人形象。
- 侧栏负责定位，主内容留白；一个区域最多一个最强主操作。进度用标签和文字，不依赖颜色区分。
- 单一焦点边框，textarea不出现内外两层粗框。键盘用户仍有清晰焦点。
- 关键操作触控目标≥44px，常用正文14–16px，辅助文字对比度≥4.5:1。
- 对话框具备可访问标题、焦点约束、Escape关闭；表单有label；禁用按钮旁说明原因。
- 375 / 768 / 1440px检查：无页面横向溢出，窄屏目标列表横向滚动，标签可滚动，目标详情可访问。
- 原生HTML/SVG，无外部字体/CDN；尊重prefers-reduced-motion。

## 12. 关键验收用例

1. 新建目标从任意一级页面可达；下一步/返回保留文本和Agent选择；创建后在目标列表、任务中心同时出现。
2. 无Agent、空目标拦截；脚本字符串按纯文本显示。
3. 商品资料未确认时不能审批；样例来源和确认时间可查看。
4. 群消息只触发一位接收者，@只允许参与者；聊天不自动修改事实或产生交付物。
5. 只准备草案目标不存在发布步骤，任务完成数不包含未发生的平台操作。
6. 正常发布流程从资料贯通复盘，任务/交付物/讨论/全局入口状态一致。
7. 审批后修改售价，旧审批失效；旧版本批准/提交被拒绝。
8. 退回无原因拦截；退回后可修改并再次审批。
9. 提交重复请求只产生一个执行ID；回读不一致后能重试核验，不能重复发布。
10. 暂停目标阻止推进，仍能讨论；暂停回复只影响回复，不冒充停止平台动作。
11. 观察前无利润结果；演示复盘显示全部费用和无基线限制；结束需要显式验收。
12. 切换目标不串消息和草稿；轮询不丢输入；刷新保留目标、版本、审批和成果。
13. 离线HTML不发网络请求即可完成主流程；服务端同流程可运行。
14. 手机端能发言、切标签、看资料和审批；键盘可操作主要流程。

## 13. 后续实施顺序

**P0 当前原型：** 验证对象、状态、群聊与任务的共存方式，并用一个虚构商品走通交互。不要在此阶段堆叠十二套岗位首页。

**P1 真实PoC：** 确定试点平台/店铺/SKU → 接权威规格/库存/成本 → 接模型与一组专业能力 → 数据触发机会 → 可解释利润/供货判断 → 真正授权上架与状态回读 → 至少一种真实经营调整 → 完整观察复盘。无广告写权限时明确人工执行并留证据。补齐真实登录、权限、审批人、数据库、任务恢复、接口幂等、审计。

**P2 场景扩展：** 在售优化、库存履约、客服反馈、平台健康；再活动与跨店复制。持续经营目标和经营总览基于实际数据成熟度建设。
